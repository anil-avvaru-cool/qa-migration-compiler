## 📊 Data Flow Analysis

### Extraction Chain (Current)
```
Java AST 
  → PageObjectExtractor (extracts page classes, methods)
  → LocatorExtractor (extracts By.xxx() calls)
  → ActionMapper (extracts method calls, limited semantic)
  → IRExtractor.extract() → generic steps with no action type
  → TestIRBuilder (receives generic steps, passes through)
  → FileWriter (outputs generic steps as-is)
```

### Root Causes

1. **ActionMapper** returns flat structure: `{type: "action", name: "click", target_name_id: "...", ...}`
   - Maps Selenium method names to action names ✓ (good)
   - But doesn't resolve action types (navigate, type, click, etc.)
   - No target ID linking to targets.json

2. **LocatorExtractor** extracts locators but:
   - Doesn't map them to page classes (context.page=null)
   - Doesn't infer semantic role (textbox, button, label, etc.)
   - Wraps selector values in extra quotes

3. **TestIRBuilder** receives generic steps and:
   - Passes them through without enrichment
   - No attempt to match steps with extracted targets
   - No inference of input data sources

4. **Pipeline** doesn't:
   - Link extracted targets to test steps
   - Assign priority/severity
   - Configure data binding
   - Infer assertions from tests

## ❓ Clarification Questions

Before implementing, I have these questions:

### Q1: Semantic Action Type Mapping
For mapping Selenium methods to IR action types:
- Should `sendKeys()` → "type"? ✓
- Should `click()` → "click"? ✓
- Should `findElement()` + `getText()` → "gettext"? OR should we skip utility methods?
- Should we infer "navigate" from `driver.get(url)` calls? OR only from explicit navigate annotations?
- For page object methods like `loginPage.enterEmail()`, should action type be inferred from method name or set to "generic"?

**Suggested approach**: Parse method names and driver calls. E.g., `enterEmail()` → "type", `click*()` → "click", `get()` → "navigate"

### Q2: Target Page Context
For extracting context.page:
- Should we only use the class where the locator is defined? (e.g., if `By.id("username")` is in LoginPage.java → context.page="LoginPage")
- What if a locator is used in a base class? Should that inherit from subclass?
- How to handle cross-page locators?

**Suggested approach**: Map each locator to its defining class directly.

### Q3: Semantic Role Inference
For inferring semantic role (textbox, button, label, etc.):
- Should we use HTML element hints from selectors? (e.g., XPath with `//input` → "textbox", `//button` → "button")
- Should we use businessName patterns? (e.g., "...Input" → "textbox", "...Button" → "button", "...Message" OR "...Label" → "label")
- What's the fallback for unknown roles?

**Suggested approach**: Use element type from XPath/CSS (".button", "input[type=text]") + businessName patterns. Fallback: "element".

### Q4: Priority & Severity Assignment
For test priority/severity that aren't in Java annotations:
- Should we use method naming patterns? (e.g., "test*Smoke*" → P0, "test*Regression*" → P2)
- Should we use suite membership? (e.g., LoginTests → P1, InventoryTests → P2)
- Should we default all to P1/Critical?

**Suggested approach**: Use method name patterns for hints, suite-level defaults, explicit annotation if available.

### Q5: Data Binding & Assertions
For tests without explicit @DataProvider:
- Should we create dummy data binding? (e.g., if test has hardcoded values)
- Should we infer assertions from `Assert.*` statements?
- Should we skip if no assertions found?

**Suggested approach**: 
- Only add dataBinding if @DataProvider annotations exist
- Extract assertions from Assert. method calls
- Leave empty if none found

### Q6: Suite Mapping
Current: 13 individual suite files (one per source file)  
Expected: 2-3 canonical suites (AUTH_SUITE, ORDER_SUITE, etc.)

Should we:
- Keep per-class suites + add canonical suites?
- Replace with canonical suites only?
- Auto-group by package?

**Suggested approach**: Create canonical suites by grouping test files by functionality (e.g., LoginTests + UserProfileTests → AUTH_SUITE, ProductSearchTests + ShoppingCartTests → ORDER_SUITE, etc.)
